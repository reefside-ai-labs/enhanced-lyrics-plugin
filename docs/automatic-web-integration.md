# Automatic Web integration investigation

Research date: 2026-10-05. Scope: server-hosted Jellyfin Web on Jellyfin 12.1 and 12.2. This document records source evidence and an implementation recommendation; it does not claim a production implementation or personal-server deployment.

## Recommendation

Register an ASP.NET Core `IStartupFilter` from our existing `IPluginServiceRegistrator`. The filter can install middleware before Jellyfin's default-file and static-file handlers, capture the generated Web index response, and insert our existing external loader before Jellyfin's scripts. Keep the Web files on disk unchanged. Normal plugin installation plus the usual Jellyfin restart and browser reload can then enable the enhanced Web player without a separate script installer, SSH access, writable Web directory, custom Docker image, or another plugin.

An isolated prototype passed transport, bridge initialization, and live playback checks on stock Jellyfin 12.2 Docker. This validates feasibility; it is not a production implementation or release. Full 12.1 transport/playback coverage and the release matrix below remain required.

## Why the hook is available

Jellyfin 12.1's `Program` registers `appHost.Init(services)` through the generic host's `ConfigureServices` before `Build`. `ApplicationHost.Init` calls the plugin manager's `RegisterServices`; the plugin manager instantiates supported, enabled plugin service registrators into the same collection. This permits our plugin to register a startup filter before ASP.NET Core builds its pipeline. [12.1 host construction](https://github.com/jellyfin/jellyfin/blob/ee91c75e777da41a9c4f4855e70adc604fbf2ef8/Jellyfin.Server/Program.cs#L170), [application initialization](https://github.com/jellyfin/jellyfin/blob/ee91c75e777da41a9c4f4855e70adc604fbf2ef8/Emby.Server.Implementations/ApplicationHost.cs#L490), [plugin service registration](https://github.com/jellyfin/jellyfin/blob/ee91c75e777da41a9c4f4855e70adc604fbf2ef8/Emby.Server.Implementations/Plugins/PluginManager.cs#L206).

The inspected 12.2 tag is commit `ca0f16eb7c195f720a1493ed469a27c4657db0c6`. Its relevant initialization and Web pipeline are unchanged: plugin registration still precedes host construction, and `Startup`, `ApplicationHost`, and `PluginManager` have no differences from the inspected 12.1 commit. The `Program` changes concern restart/shutdown exception handling. [12.2 host construction](https://github.com/jellyfin/jellyfin/blob/ca0f16eb7c195f720a1493ed469a27c4657db0c6/Jellyfin.Server/Program.cs#L180), [12.2 Web pipeline](https://github.com/jellyfin/jellyfin/blob/ca0f16eb7c195f720a1493ed469a27c4657db0c6/Jellyfin.Server/Startup.cs#L174).

ASP.NET Core 10 receives the DI collection of startup filters, wraps the application's configure action in reverse registration order, invokes it, then builds the pipeline. A filter that calls `UseMiddleware` before its supplied `next(app)` adds an outer middleware. Relative ordering between different plugins depends on registration order, so our behavior must compose in either position. [.NET 10 GenericWebHostService](https://github.com/dotnet/aspnetcore/blob/v10.0.0/src/Hosting/Hosting/src/GenericHost/GenericWebHostService.cs#L121).

## Existing working approaches

Custom Logo independently registers a startup filter and transforms index responses without modifying disk files. Its middleware deliberately calls the downstream pipeline before transforming the result so other plugins' edits survive. It also handles compression negotiation, rewritten validators, configured base URLs, and full response-body feature replacement. This is a useful engineering reference; our implementation can be much smaller because it adds only one external script. [Pinned startup filter](https://github.com/WimWamWom/jellyfin-plugin-custom-logo/blob/2c4f99b96ab4c1ceafacb2b717c97a104c1e8dbe/Jellyfin.Plugin.CustomLogo/Injection/CustomLogoStartupFilter.cs), [pinned middleware](https://github.com/WimWamWom/jellyfin-plugin-custom-logo/blob/2c4f99b96ab4c1ceafacb2b717c97a104c1e8dbe/Jellyfin.Plugin.CustomLogo/Injection/CustomLogoMiddleware.cs).

File Transformation's current implementation also uses plugin service registration and a startup filter. Its public API allows other plugins to register transformations by reflection, avoiding plugin assembly-load-context coupling. Depending on that API would add another installation requirement, so it is not necessary for our single loader. Its broader transformation service remains useful as an interoperability test target. [Pinned registration](https://github.com/IAmParadox27/jellyfin-plugin-file-transformation/blob/2dd4279bc7aedd082de0639278f9142ead229a52/src/Jellyfin.Plugin.FileTransformation/PluginServiceRegistrator.cs), [pinned middleware](https://github.com/IAmParadox27/jellyfin-plugin-file-transformation/blob/2dd4279bc7aedd082de0639278f9142ead229a52/src/Jellyfin.Plugin.FileTransformation/Infrastructure/FileTransformationMiddleware.cs), [reflection API](https://github.com/IAmParadox27/jellyfin-plugin-file-transformation/blob/2dd4279bc7aedd082de0639278f9142ead229a52/README.md#referencing-this-as-a-library).

## Implementation constraints

- **Request selection and base URL:** intercept only the server's exact configured `/web/` and `/web/index.html` paths. The filter runs before Jellyfin's `Map(BaseUrl)`, so `Request.Path` still includes that prefix. Account for any preexisting `PathBase`. Leave `/web` without the slash to Jellyfin's redirect, which is needed for relative assets. Do not intercept API, streaming, nested lookalike paths, or non-GET/HEAD methods. [Jellyfin mapping and static files](https://github.com/jellyfin/jellyfin/blob/ca0f16eb7c195f720a1493ed469a27c4657db0c6/Jellyfin.Server/Startup.cs#L174).
- **Capture all writes:** replace `IHttpResponseBodyFeature`, not only `Response.Body`, and restore it in `finally`. Static files use `SendFileAsync`. The built-in `StreamResponseBodyFeature` correctly routes that call through its supplied stream and adapts `BodyWriter`; its `StartAsync` flushes that stream rather than starting the original socket response. A custom feature is unnecessary for normal buffering. Use a bounded strategy if expanding beyond the small trusted index, and flush adapted writers before reading captured bytes. [.NET response feature](https://github.com/dotnet/aspnetcore/blob/v10.0.0/src/Http/Http/src/StreamResponseBodyFeature.cs#L78).
- **HEAD and ranges:** the static handler emits no body for HEAD, so the ordinary capture cannot derive transformed length or validators. Either obtain the equivalent GET representation internally and suppress the final HEAD body, or deliberately pass HEAD through and avoid claiming it has transformed metadata. Strip range/if-range for rewritten GETs and return a complete representation; remove stale `Content-Range`/`Accept-Ranges`. Partial HTML cannot safely be injected. [.NET static-file behavior](https://github.com/dotnet/aspnetcore/blob/v10.0.0/src/Middleware/StaticFiles/src/StaticFileContext.cs#L280).
- **Compression:** Jellyfin's response-compression middleware sits downstream. Temporarily remove `Accept-Encoding` while capturing, restore it afterward, and serve identity encoding or explicitly negotiate/recompress the final bytes. Never decode a compressed body as UTF-8. Other outer/inner transformation plugins may compress too; test both registration orders and inspect `Content-Encoding`, rather than assuming stripping the request always controls every plugin.
- **Cache correctness:** downstream disk ETag/Last-Modified describe different bytes. Temporarily remove conditional headers that would produce a bodyless 304; remove invalid validators or generate an ETag from the transformed representation. Update `Content-Length`; use `no-cache` or `no-store`. Consider `If-Match`/`If-Unmodified-Since` as well as common revalidation headers. Restore request headers in `finally` so outer middleware sees the original request.
- **Loader ordering/idempotence:** insert before the first Jellyfin boot script, without `async` or `defer`, because our playback bridge hooks Webpack before its modules execute. Detect the existing marker/loader so a previously manually patched installation gets only one copy. Use the existing relative `../EnhancedLyrics/Assets/enhanced-lyrics.js` path from the Web document to preserve configured base paths; verify unusual `<base>` markup. If known insertion anchors are absent, pass the original HTML through and log a clear diagnostic.
- **CSP:** an external same-origin script works with policies allowing same-origin scripts, but a proxy can impose nonce/hash-only restrictions. Do not weaken a user's policy automatically. Copy a validated document nonce if supported, otherwise diagnose that the loader was blocked. A response transformer cannot universally defeat proxy CSP or separately hosted client HTML.
- **Other plugins and failure:** transform downstream output rather than short-circuiting with a disk copy. Preserve their markup, headers, redirects, errors, and non-HTML responses. Restrict rewrite to successful index HTML; always restore features and request headers, honor cancellation, and serve stock output if our insertion fails. A globally disabled plugin should stop inserting on subsequent loads. Existing tabs can use the current runtime disable mechanism.
- **Versions and topology:** middleware availability is verified for 12.1/12.2 source, not a permanent Jellyfin Web extension contract. Verify catalog ABI/build compatibility separately from the Webpack bridge. Automatic injection reaches only Web HTML hosted by the same Jellyfin server; a separate Web host, native app, or reverse proxy that independently serves index HTML needs its own supported client integration.

## Alternatives

| Approach | Assessment |
| --- | --- |
| Patch `index.html` on plugin startup | Reject as default: fails with read-only container/package Web files, mutates shared installation state, needs cleanup/permissions, and updates can remove edits. |
| Depend on File Transformation | Technically viable, but adds a second plugin install and version/reflection dependencies. Not needed for our narrow use case. |
| Short-circuit index request with our own disk copy | Simpler capture, but bypasses downstream middleware and other plugins' transformations. Avoid unless explicitly documented as incompatible. |
| ASP.NET response middleware via startup filter | Preferred: available during registration, no disk changes, composes with downstream response changes, covers stock Docker installation. |

## Minimum verification before release

Use stock Jellyfin images for both supported versions with an unmodified, read-only Web index. Verify installation/restart/reload boots the bridge and live lyrics playback, then confirm index bytes on disk remain identical. Exercise `/web` redirects, `/web/`, explicit index, query strings, BaseUrl, identity/gzip/brotli requests, conditional headers, HEAD, Range, duplicate manual loader, disable/uninstall, invalid markup, and unchanged media/API traffic. Include a second response-transforming filter both inside and outside ours. Report server plugin loading, automatic index integration, and browser playback connection separately so an active server plugin cannot imply a working client.

## Local prototype results

Tested 2026-10-05 using freshly pulled `jellyfin/jellyfin:latest`, reporting Jellyfin 12.2.0. Image digest: `sha256:357724bf0ae27a672c7cbaa899db2d9abeb13dbd8657ccce750258a4c059d037`. Prototype source/build lived outside the repository at `/private/tmp/enhanced-lyrics-auto-docker`; only this report is a repository change. The image added plugin DLLs and a test entrypoint that copies them into the writable plugin directory, simulating installation. It contained no Web patching layer.

- Container `enhanced-lyrics-auto-probe`, loopback port 8099, separate ignored config/cache, synthetic media read-only. Container root filesystem used Docker `--read-only`; only config/cache and temporary directories were writable.
- `IStartupFilter` registered through the plugin service registrator successfully ran before Jellyfin static-file serving. `/web/` and `/web/index.html` responses inserted the existing loader before the first Jellyfin script. Combined compression negotiation, future `If-Modified-Since`, and byte-range requests yielded full, uncompressed 200 HTML without the original ETag.
- Stock index on disk exactly matched the original image before and after playback. SHA256: `692ac1582fd119b0ec4712de52ec3fc82375bcd844741467df050372ccde5b40`. The file contained no EnhancedLyrics loader.
- API smoke checks passed: authentication, rich/legacy lyrics, TTML translation/romanization variants, ELRC fallback, and disable/re-enable.
- Normal browser document navigation initialized `window.EnhancedLyrics.bridgeReady` without a DOM patch. Playing the Visual Features fixture and opening Lyrics mounted one Braccato renderer with enhanced mode active. Audio advanced from 5.638 to 8.137 seconds over a 2.5-second sample, renderer time was 8.045 seconds, and media error code was 0. Translation/romanization controls and the enhanced duet view were visible. Playback was paused after testing.
- Visual screenshots were inspected at `/Users/michaelteuscher/.t3/userdata/browser-artifacts/browser-screenshot-127-0-0-1-muw1nkg8-ce8587a1.png` (translations/romanization) and `browser-screenshot-127-0-0-1-muw1mr1s-67e41b72.png` (duet/unison). These are local evidence artifacts, not committed media.
- A separate ASP.NET 10 harness additionally passed root/BaseUrl paths, query strings, conditional/range requests, untouched JavaScript, and disable behavior against a read-only physical index. Its HEAD check only proved a bodyless response; matching transformed GET headers remains unimplemented and unverified.

The prototype deliberately omits production concerns: bounded response buffering, complete HEAD/precondition semantics, idempotence for existing manual installs, and interoperability with another transformation filter. It must not be shipped as-is. No changes were made to the personal NAS, production plugin source, or published package.
